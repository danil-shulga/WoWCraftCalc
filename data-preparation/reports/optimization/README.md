## Методика

Команды из корня проекта:

```shell
node scripts/measure-performance.mjs --full --output data-preparation/reports/optimization/optimization-baseline.json
node scripts/measure-performance.mjs --full --compare data-preparation/reports/optimization/optimization-baseline.json --output data-preparation/reports/optimization/optimization-stage-1.json
```

Первую команду выполняли до изменения расчётов. Не перезаписывать исходный
отчёт после оптимизации; для следующих этапов указывать новые выходные файлы.
Сценарий использует установленный Vite для загрузки TypeScript без HTTP-сервера,
не обращается к сети, store или хранилищу браузера. Новые зависимости не добавлены.

- 3 прогревочных запуска, затем 20 измерений каждой операции. В JSON сохранены
  медиана, p95, минимум и максимум, окружение, время запуска и исходная ревизия.
  Ревизия обозначает HEAD; незакоммиченные изменения этапа описываются ниже.
- Входы — отдельные полные базы Forever, TBC и Classic. Для каждого замера
  сохранены SHA-256 файла и разобранных данных, размер JSON, gzip и Brotli
  с настройками Node.js по умолчанию. Это не измерение реального HTTP-трафика.
- Малые каталоги построены из первых 100 рецептов со всеми прямыми реагентами,
  большие — из всех рецептов базы. Один рецепт на продукт, только рёбра
  к меньшему игровому ID: так получается воспроизводимый ациклический граф.
  Кандидат выхода использован как синтетическое количество; это тестовый набор,
  а не подтверждённый игровой выход и не резервная копия пользовательских данных.
- Цены детерминированы ID; часть покупок имеет неизвестную цену. Доступны
  профессии своей версии, приоритет цен — `individual`, рынок и снимок TSM
  отсутствуют. Сохранённые хеши каталога проверяются при сравнении.
- Отдельный набор `shared-chain` содержит 210 предметов: начальный материал,
  девять вложенных промежуточных рецептов и 200 продуктов с общим реагентом.
  Он проверяет повторное использование цепочки, без игровых метаданных.
- Отдельно измеряются чтение файла, JSON-разбор, валидация, создание индекса,
  серия поисков RU/EN, снимки каталога и распыления и прямой поиск по каталогу.
  Чтение файла выполняется с системным файловым кэшем; холодная сетевая загрузка
  и память браузера этим сценарием не измеряются.
- `--compare` требует совпадения всех входов и контрольных сумм результатов.
  Время не проверяется порогом: его оценивают по повторным запускам в том же
  окружении. Браузерные замеры должны идти отдельно, в одном профиле на `5174`.

Размеры наборов: Forever — 162/2344 предмета и 41/1528 рецептов,
TBC — 162/2363 и 39/1280, Classic — 162/1436 и 39/702
(малый/большой каталог соответственно).

## Этап 3: поиск без пересчёта каталога

`ItemsPage.tsx` готовит снимки по полному набору предметов раздела;
`selectSectionItems` в `craft.selectors.ts` отделяет состав раздела от языка
и пользовательского порядка. Поиск фильтрует готовые строки. Изменения
каталога, профессий, версии и контекста цен остаются зависимостями расчётов.
Формулы, формат хранения и поведение редакторов не менялись.

`ItemsPage.calculations.test.tsx` сначала воспроизвёл 5 запусков снимка
при начальном открытии и четырёх изменениях запроса. После правки остаётся
1 начальный запуск, без новых при вводе, очистке, смене языка, перестановке
и изменении количества плана. Это проверено для крафтов, реагентов, избранного
и распыления. Отдельный RTL-сценарий при активном поиске проверяет видимую
себестоимость после изменения вложенной цены, рецепта, способа получения,
профессий, рынка, показателя, приоритета и снимка TSM.

Профильный запуск до расширения тестов на реагенты и избранное — 10 файлов,
75 тестов. Итоговый `npm run check` — TypeScript, ESLint, Prettier,
68 файлов и 718 тестов успешно. `npm run build` — успешно, с прежними
предупреждениями Zod и размера JS-бандла. Проверки выполнялись с тем же
временным каталогом Vitest внутри `node_modules`, без изменения конфигурации.

Браузерный [отчёт этапа 3](optimization-ui-stage-3.json) получен после проверок,
без параллельного запуска инструментов, в том же профиле и на том же наборе.
Относительно этапа 2 медианы в мс: открытие 79,9 → 81,1;
серия поисков 160,2 → 149,8; изменение количества 45,4 → 45,6;
изменение цены при узком поиске 3,0 → 3,3. p95 серии поиска — 280,5 → 250,6.
Медиана рендера серии в Profiler — 108,8 → 102,9 мс. Разброс браузерных
измерений заметный: эти числа описывают данный запуск, а не гарантированное
ускорение каждого ввода. Надёжный результат этапа — отсутствие лишних
запусков расчёта, закреплённое тестами. Сохранённый каталог браузера не изменился.

Компромисс: изменение цены при узком поиске теперь готовит прибыль для всего
раздела; поиск после него использует актуальный снимок без нового расчёта.
Это увеличивает работу при правках цен на фоне узкого запроса. На 100 продуктах
получено 3,0 → 3,3 мс; для больших каталогов этот сценарий стоит учитывать
при последующих замерах. Мобильные раскладки и разные размеры окна не проверялись.

с фильтрацией заранее подготовленных строк на том же наборе: 2348 предметов

из 5 запросов: Forever 74,174 → 0,894 мс, TBC 74,686 → 0,923 мс,
Classic 44,922 → 0,546 мс. Обе реализации включены в один запуск;
контрольные суммы совпали. Подготовка строк занимает соответственно
13,316, 13,562 и 7,874 мс и не входит во время готового поиска.
Это замер операций с именами, не полного рендера `ItemsPage`.

Оценка удерживаемой кучи Node после принудительного GC:

- Индекс справочника Forever: 982 376 → 1 043 400 байт; TBC:

## Этап 5: компактные справочники (18.10.2026)

`scripts/versioned_databases/compact.mjs` использует фактическую runtime-схему
через Vite SSR без HTTP-порта. Строгий полный контракт, сериализация проекции
и глубокое равенство после повторного разбора проверяются для всех входов
до записи результатов. `release.py` сохраняет полные форматированные артефакты

## Этап 7: событийная оценка localStorage (18.10.2026)

`src/app/useLocalStorageUsage.ts` хранит один числовой снимок для всех
потребителей `useSyncExternalStore`. Подключение первого потребителя выполняет
обход; чтение снимка при рендере не обращается к Storage. Общие обработчики
работают только пока есть подписчики и снимаются после последнего.
Повторное монтирование обновляет снимок, в том числе после записей без слушателей.
Таймер 2000 мс удалён. Обновления выполняются после уведомления своей вкладки,
по `storage` и `focus`; одинаковое число байт не вызывает новый рендер.

`src/store/local-storage-events.ts` отправляет событие после успешной операции.
К нему подключены все производственные записи в localStorage: обычное сохранение,
атомарное восстановление/сброс через `createCraftStorage`, удаление старого ключа
и текущей записи. `tsm-loader.ts` уведомляет один раз после серии удалений старого
кэша, включая удаления до частичного отказа. SessionStorage не учитывается.
Чтение для измерения защищено: его ошибка даёт `null`, успешная запись остаётся
успешной. Блокировка повреждённых данных и порядок «сначала сохранить, затем
применить» не менялись. Сторонняя запись своей вкладки без уведомления видна при
фокусе; нового писателя нужно подключать к уведомлению. Это сознательная граница
событийного механизма, глобальный Storage API не подменяется.

Повторяемая проверка `src/app/useLocalStorageUsage.test.tsx` на 100 ключах:

- За минуту простоя, заданную fake timers, вызовы `Storage.key()`:
  3000 до → 0 после. Удалены 30 полных обходов в этом сценарии.
- При 20 перерисовках потребителя: 4000 до → 0 после.
  `getSnapshot` теперь возвращает последнее число, не измеряет заново.
- При двух потребителях и двух ключах одно уведомление вызывает 2 обращения
  к `key()`, обновляя оба результата. После размонтирования последнего
  уведомление, `storage` и `focus` больше не читают Storage.

Это подсчёт операций в RTL/jsdom, не оценка задержки пользователя или мощности CPU.
Исходный запуск воспроизвёл две ошибки новых проверок на прежней реализации;
после замены механизма обе проходят без порогов времени.
`local-storage-writes.test.tsx` проверяет реальные действия store, удаление ключей,
ошибки записи/удаления, атомарный отказ восстановления, заблокированные записи,
ошибку измерения после успешной записи, пакетную и частичную очистку старого
TSM-кэша и независимость sessionStorage. Сохранены отдельные domain-тесты UTF-16,
Unicode, всех ключей сайта и приблизительного остатка от 5 МиБ.

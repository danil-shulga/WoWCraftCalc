# План: приоритетные цены и запасной источник

Статус: реализовано 17.10.2026. Основание — пункт 8 в [TODO](../TODO.md).
Ниже сохранён исходный план; текущее поведение описано в [документации TSM](tsm-tbc.md).

Проверки реализации: `npm run check` — 66 файлов, 701 тест; `npm run build` — успешно.
На `http://localhost:5174/` проверены приоритет TSM с ручной подстановкой,
длинное название, массовый ввод и переход в планировщик с сохранением режима.
Обратная подстановка и черновики проверены React Testing Library.

Цель: при отсутствии приоритетной цены использовать второй источник и назвать
переключатель «Приоритетные цены» с вариантами «Заданные» и «TSM».

## Предлагаемое поведение

- «Заданные» сохраняет смысл текущего режима `individual`: сначала источник,
  выбранный у предмета отдельно для покупки и продажи (`manual` либо `tsm`),
  затем второй источник. Отсутствующий выбор источника означает `manual`.
  Это не принудительный приоритет ручных сумм для всех предметов.
- «TSM» (`tsm`) сначала использует выбранный показатель TSM, затем ручную сумму
  соответствующего направления. Индивидуальные настройки при этом сохраняются.
- Подстановка происходит только при `null`. Ручная цена `0` — полноценная цена,
  которая не должна заменяться TSM. Если обе цены отсутствуют, результат — `null`.
- Покупка и продажа разрешаются независимо. Вторым источником для покупки
  не может стать ручная цена продажи и наоборот.
- Проверки TSM остаются в `getTsmPrice`: свой рынок, снимок, версия источника,
  игровой ID и выбранный показатель. Отсутствие любого условия разрешает
  подстановку ручной цены, но не использование чужого снимка или другого показателя.
- Classic, Forever и вызовы без `PriceContext` продолжают использовать ручные цены.
- Выбор режима и подстановка не записывают полученные цены в каталог, не меняют
  индивидуальные источники и способы получения. Формат сохранения и backup остаётся v1.
- Подписи TSM относятся к фактически используемой цене, включая подстановку TSM
  вместо отсутствующей ручной. Когда обе цены неизвестны, подпись «используется TSM»
  не показывается.

## Что уже есть

- [tsm.ts](../src/domain/tsm.ts): `getTsmPrice` проверяет доступность TSM;
  `resolveItemPrice` выбирает цену без запасного источника; `usesTsmPrice`
  определяет выбранный источник, даже если его цены нет.
- [calculations.ts](../src/domain/calculations.ts) и
  [planner.ts](../src/domain/planner.ts) используют эти функции для сумм
  и признаков источника. Распыление также получает цены через `resolveItemPrice`.
- [PriceModeSelector](../src/features/tsm/PriceModeSelector.tsx) общий для каталога
  и планировщика; текущие подписи — «Цены для расчётов», «Выбранные», «По TSM».
- [ItemPriceCell](../src/components/item-tree/RootItemRow/ItemPriceCell.tsx)
  и [ShoppingList](../src/features/planner/ShoppingList.tsx) показывают источник.
  Массовый ввод редактирует ручные суммы, а не результат разрешения цены.
- В `tsm.test.ts` и `planner.test.ts` есть проверки старого запрета подстановки:
  их ожидания нужно заменить вместе с изменением поведения.

## 1. Единый выбор суммы и фактического источника

Файл: `src/domain/tsm.ts`; тесты: `src/domain/tsm.test.ts`.

1. Ввести внутри модуля общую реализацию выбора, возвращающую сумму и её источник.
   Если обе суммы отсутствуют, возвращать `null` и отсутствие фактического источника.
   Достаточно внутреннего результата; новый публичный контракт не требуется.
2. Сохранить сигнатуру `resolveItemPrice`, возвращать из неё выбранную сумму.
3. Сохранить сигнатуру `usesTsmPrice`, определять через ту же реализацию,
   получена ли итоговая сумма из TSM. Не вызывать функции друг через друга по кругу.
4. Перед изменением повторно проверить все вызовы обеих функций, фикстуры
   и ожидания: изменение смысла `usesTsmPrice` затрагивает отображение источника.

Проверки: оба режима × оба индивидуальных источника × покупка/продажа;
обе цены есть, нет приоритетной, нет запасной, нет обеих; ручной ноль.
Отдельно: нет рынка/снимка/ID/предмета/показателя, чужой рынок или версия,
отсутствующая версия источника, оба показателя, Classic/Forever и отсутствие контекста.
Сумма и признак TSM должны соответствовать друг другу во всех случаях.

## 2. Сквозные расчёты и отображение источника

Проверяемые файлы: `src/domain/calculations.ts`, `src/domain/planner.ts`,
`src/domain/disenchanting.ts`, `src/domain/disenchanting-catalog.ts`,
`src/components/item-tree/RootItemRow/ItemPriceCell.tsx`,
`src/features/planner/ShoppingList.tsx` и ближайшие тесты.

1. Убедиться, что единый выбор применяется к вложенным реагентам, сценариям
   профессий, выбору купить/крафтить, бюджету, выручке, прибыли и распылению.
2. Проверить `purchaseIsTsm`, `saleIsTsm` и `ShoppingLine.priceSource`:
   ручная подстановка не помечается TSM, подстановка TSM помечается.
   Существующие типы достаточно сохранить: при неизвестной цене TSM не отмечать.
3. Добавить сквозные тесты расчётов на оба направления подстановки,
   смешанные источники и оставшиеся неизвестные цены. Обновить тест планировщика,
   который сейчас требует неизвестный бюджет при доступной ручной сумме.
4. Через React Testing Library проверить подписи строки и закупки, массовый ввод,
   сохранение и отмену. При подстановке TSM ввод по-прежнему меняет ручной черновик;
   до сохранения каталог не меняется, после сохранения цена разрешается заново.

Код потребителей изменять только там, где общей правки выбора недостаточно.
Редактор сохраняет текущие флажки источников и правила доступности полей.

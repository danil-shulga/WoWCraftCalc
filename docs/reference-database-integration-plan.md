# План интеграции локальной базы CraftCalc

## Цель и границы первой версии

Добавить выбор крафта или реагента из подготовленного JSON в существующее окно
добавления предмета. Пользователь ищет предмет, выбирает рецепт, проверяет состав и
выход, затем подтверждает добавление. Текущие способы «Импорт из Wowhead» и
«Добавить вручную» сохраняются.

Это план для реализации в новом чате. Код приложения в рамках подготовки плана не
изменён. Описанный сценарий — рекомендуемое решение; массовое заполнение каталога,
автоматический подбор вложенных рецептов и изменение расчётов в первую версию не
входят.

## Подготовленные данные

- Файл: `public/data/craftcalc-db.1.60.1.70338.json`.
- Формат: `craftcalc-reference-database`, `schemaVersion: 1`.
- Сборка: `1.60.1.70338`; источник иконок — Wowhead `forever`.
- 2 344 уникальных предмета: 1 977 результатов крафта, 530 реагентов,
  163 предмета входят в обе группы.
- 1 984 рецепта, 630 имеют требования инструментов.
- У всех предметов заполнены ссылки на иконки; изображения размещены на CDN
  Wowhead. В файле 1 278 уникальных ссылок, размер примерно 3,6 МБ.
- 326 эффектов исключены из рецептов из-за отсутствующих предметов. Они находятся
  в `excludedRecipeEffects` и не должны предлагаться для импорта.

У предмета оставлены только `itemId`, `names`, `iconUrl`, `qualityId`,
`recipeSpellIds`, `vendor`, `bondingId`. Ключ `items` — строковое представление
числового ID. Ключ `recipes` — строковое представление `spellId`.

У рецепта есть результат, профессия, состав, сведения о выходе, инструментах,
навыке и источнике. Некоторые предметы имеют несколько рецептов. Присутствие в
таблицах клиента не гарантирует доступность рецепта в игре.

**Все `output.quantity` сейчас равны `null`.** `baseQuantityCandidate` —
неподтверждённый кандидат из эффекта, а не готовое значение для расчётов. Не
превращать его автоматически в подтверждённый выход. Есть нулевые базовые значения
и переменный выход.

## Существующие точки интеграции

Перед изменениями перечитать реальные файлы и ближайшие тесты: проект может
измениться между чатами.

- `src/features/item-editor/ItemAddModal.tsx`: сейчас две вкладки, Wowhead и ручное
  добавление. Здесь добавить вкладку «Из базы».
- `src/pages/ItemsPage.tsx`: общая страница для крафтов и реагентов, связывает UI с
  действиями store. Не создавать вторую аналогичную страницу.
- `src/store/useCraftStore.ts`: `createItem`, `importRecipe`, `findImportedItem`.
  `importRecipe` уже создаёт результат и реагенты атомарно, сохраняет цены,
  вложенные рецепты реагентов и выбор получения; проверяет циклы перед записью.
- `src/domain/item.types.ts`, `item.schema.ts`: рабочая модель хранит один активный
  рецепт на предмет; локальные ID — строки, обычно UUID.
- `src/domain/item-names.ts`: использовать существующий поиск по RU/EN и
  нормализацию названий.
- `src/domain/recipe-validation.ts`: использовать существующую защиту графа.
- `src/store/persistence.ts`: импорт резервной копии заменяет данные. Он не
  предназначен для загрузки справочника.
- `src/features/wowhead-import/WowheadImportForm.tsx`: ориентир для предпросмотра,
  подписей происхождения выхода и подтверждения импорта.
- `src/components/ui`: переиспользовать поля поиска, диалог, вкладки и кнопки.
- `vite.config.ts`: сохранить `base: './'` и GitHub Pages.

## Этап 1. Контракт и проверка справочника

Предлагаемые новые файлы: `src/domain/reference-database.types.ts`,
`reference-database.schema.ts`, `reference-database.test.ts`.

1. Определить типы справочника отдельно от рабочей модели `Item`. Не превращать
   всю базу в `ItemCatalog` при запуске приложения.
2. Определить Zod-схему для используемых полей, формата, версии схемы, сборки и
   версии Wowhead. Проверять сетевой JSON как `unknown`.
3. После разбора проверить соответствие ключей ID, существование результатов и
   всех реагентов, положительные целые количества, отсутствие повторов реагента,
   ссылки `recipeSpellIds` и обратную связь результата с рецептом, профессии.
4. Не требовать, чтобы все ID инструментов находились в `items`: предметы,
   являющиеся только инструментами, намеренно не включены в каталог. Категории
   инструментов также не являются ID предметов.
5. Поддерживать неизвестный выход без подстановки нуля или единицы в исходные
   данные. Не пытаться валидировать полный справочник как рабочий граф: набор
   альтернативных рецептов может содержать циклы, даже если выбранный граф допустим.
6. Не менять формат самого подготовленного файла без необходимости. Поля,
   не используемые первой версией UI, могут оставаться в справочнике.

Проверки: короткие фикстуры для корректного набора, повреждённого количества,
отсутствующего реагента, неверной версии, нескольких рецептов и внешнего
инструмента. Отдельно проверить текущий JSON целиком новой схемой и связями.

## Этап 2. Загрузка по требованию и индексы

Предлагаемые файлы: `src/features/reference-database/reference-database-loader.ts`,
`reference-database-loader.test.ts`; индексы и чистые выборки разместить в domain.

1. Загружать файл при первом открытии вкладки «Из базы», через
   `${import.meta.env.BASE_URL}data/craftcalc-db.1.60.1.70338.json`.
2. Не встраивать JSON в JS-бандл и не загружать при старте всего приложения.
3. Кешировать успешную загрузку в памяти на время сессии; объединять одновременные
   запросы. После ошибки разрешить повторную попытку.
4. Предусмотреть таймаут запроса, ошибки HTTP/JSON/схемы и понятную кнопку повтора.
   После закрытия окна не обновлять его состояние; отмена одного потребителя не
   должна ломать общий запрос другого потребителя.
5. Один раз построить индексы по ID, названиям RU/EN, профессии, результату рецепта
   и множеству реагентов. Производные индексы не сохранять в localStorage.
6. Для раздела крафтов предлагать результаты рецептов; для реагентов — предметы,
   используемые в составах. Не смешивать эти группы автоматически.

Проверки: корректный путь при размещении в подпапке, один запрос для нескольких
потребителей, повтор после ошибки, отсутствие изменений пользовательского store,
поиск на обоих языках и переключение раздела.

## Этап 3. Преобразование и действия store

Предлагаемый чистый адаптер: `src/domain/reference-database-import.ts` с тестами.
Каталог изменять только действиями `src/store/useCraftStore.ts`.

1. Преобразовывать выбранный рецепт в существующий `RecipeImportData` и по
   возможности использовать `importRecipe`, не копируя его логику в компонент.
   Расширить входные данные импорта ценами по умолчанию из базы; применить их
   внутри того же атомарного обновления, включая результат и все реагенты.
2. Передавать `names`, `iconUrl`, числовой `wowheadItemId` и
   `wowheadVersion: 'forever'` явно. Не присваивать версию из текущей настройки
   пользователя. Раздел базы подписать «Forever»; не выдавать данные за Classic/TBC.
3. Не заменять локальные UUID числовыми ID базы. Сопоставлять через существующий
   `source`, учитывая версию игры, затем допустимое единственное совпадение имени.
   Неоднозначное сопоставление показать пользователю, без молчаливого объединения.
4. Для добавления отдельного реагента нужен отдельный атомарный action, например
   `addReferenceItem`, который переиспользует существующее сопоставление,
   добавляет раздел `reagents` и возвращает локальный ID. Не вызывать `createItem`
   без проверки, если предмет уже существует.
5. Цены NPC из `vendor` использовать как цены по умолчанию: при незаданном
   `purchasePriceCopper` брать `vendor.baseBuyPriceCopper`, при незаданном
   `salePriceCopper` — `vendor.sellPriceCopper`. Применять это при добавлении
   предмета и повторном импорте к каждому незаполненному полю отдельно. Незаданная
   цена — `null`; любое уже сохранённое число, включая `0`, сохранять. Нулевую
   цену из базы также переносить как `0`; если исходная цена отсутствует, оставлять
   `null`. Отдельный справочный блок цен NPC не нужен.
6. Повторный импорт сохраняет пользовательские цены и ручной выбор получения.
   Замена активного рецепта результата требует понятного предпросмотра; цена и
   вложенные рецепты существующих реагентов сохраняются.
7. Добавлять выбранный рецепт и его непосредственные реагенты. Не подтягивать
   рекурсивно все рецепты реагентов; их можно добавить отдельным выбором позднее.
8. Проверять рабочий граф до единственного обновления. При ошибке или отмене не
   добавлять даже часть предметов. Действующий выбранный рецепт должен быть
   единственным активным рецептом результата.

Первая версия может не расширять persisted-модель: `qualityId` и `bondingId`
доступны в предпросмотре через справочник, а цены из `vendor` записываются в
существующие поля цен только при отсутствии значения. Если потребуется хранить
`spellId` выбранного рецепта или дополнительные свойства внутри `Item`, отдельно
согласовать типы, Zod-схемы, нормализацию, версии persistence/экспорта и
совместимость старых резервных копий. Не добавлять поля только ради отображения
справочника.

Проверки: повторный импорт без дублей, разные версии игры, неоднозначность,
подстановка цен из базы для новых предметов и полей с `null`, сохранность заданных
цен (включая `0`), независимое заполнение цены покупки и продажи, перенос нулевой
цены из базы, сохранность вложенных рецептов, добавление отдельного реагента,
цикл и полное отсутствие частичной записи при отказе.

## Этап 4. Вкладка «Из базы» и предпросмотр

Предлагаемые файлы: `src/features/reference-database/ReferenceDatabaseForm.tsx`,
одноимённые CSS и тесты. Подключить через `ItemAddModal` и `ItemsPage`.

1. Добавить третью вкладку, сделать «Из базы» рекомендуемым способом добавления.
   Существующие способы сохранить.
2. Показать состояния загрузки, ошибки и повтора, поиск RU/EN и фильтр профессии.
   Выдачу ограничить страницами, например по 50 результатов, без новой зависимости
   для виртуализации. Иконки загружать лениво только у отображаемых результатов.
3. Для выбранного крафта показать результат, профессию, состав с количествами,
   иконки и альтернативные рецепты. Не выбирать произвольно первый рецепт, если
   вариантов несколько: пользователь выбирает явно.
4. Для реагента разрешить добавление самого предмета без рецепта. Если он
   изготавливается, предложить дополнительный выбор рецепта явно.
5. Выход: сохранённое локальное значение подписывать «Сохранённое значение»;
   неподтверждённый кандидат — «Предположение из базы»; при отсутствии значения
   показывать редактируемое `1` с подписью «По умолчанию». Перед записью пользователь
   подтверждает положительное целое значение общей кнопкой импорта.
6. Для переменного выхода показывать предупреждение: текущая модель принимает
   фиксированное количество. Не вычислять диапазон или среднее из `Variance` без
   отдельной проверки и задачи на расчёты.
7. Инструменты показывать отдельным блоком, не включать в стоимость партии.
   Неизвестную категорию подписать как неизвестную, без выдуманного названия.
   Отсутствие строки инструментов не выдавать за доказательство отсутствия всех
   условий изготовления.
8. На ошибку изображения использовать существующий placeholder. Восстановить
   фокус после закрытия, поддержать клавиатуру и Tab/Escape. Интерфейс и визуальные
   проверки ориентировать на desktop; поддержка узкого экрана в задачу не входит.
9. До подтверждения не менять каталог. После успеха закрыть окно и показать
   количество добавленных/переиспользованных предметов понятным сообщением.

Проверки UI: поиск, выбор альтернативы, редактирование выхода, добавление
реагента, отмена, закрытие во время загрузки, повторный импорт, ошибка графа,
сломанная картинка, длинные названия и клавиатура на desktop.

## Этап 5. Итоговая проверка и сдача

- Запустить профильные тесты после каждого небольшого изменения.
- После завершения кода выполнить `npm run check` и `npm run build`.
- Проверить, что база копируется в `dist/data`, а приложение загружает её по пути
  с учётом `BASE_URL`, в том числе при размещении в подпапке GitHub Pages.
- Проверить браузерный сценарий: выбрать «Венец из ткани Грёз» (`itemId: 10041`,
  `spellId: 12092`), подтвердить выход, увидеть рецепт и иконку; задать цены,
  переимпортировать и убедиться в сохранении цен; перезагрузить страницу и
  восстановить каталог.
- Для `spellId: 25146` проверить, что кандидат выхода `3` не подписан как
  подтверждённый, а категория инструмента `12` не добавлена к расходуемым реагентам.
- Проверить, что цены из базы заполняют только поля с `null`, в том числе у
  существующих реагентов; заданные пользователем цены и `0` не меняются. После
  перезагрузки подставленные цены должны сохраняться.
- Убедиться, что весь справочник не записан в localStorage, а импорт/экспорт
  существующих резервных копий работает по-прежнему.
- Если проверки не запускаются из-за среды, сообщить фактическое ограничение и
  не объявлять их успешными. Ранее Vite потребовал запуск вне песочницы из-за EPERM.
- После каждого изменения сообщать по-русски изменённые файлы, цель и выполненные
  проверки. Коммит и push не делать без прямой просьбы.

## Отложенные задачи

Подтверждение выхода из DB2, получение названий категорий инструментов через
TotemCategory, хранение нескольких активных рецептов, автоматический выбор
вложенных способов получения, локальное скачивание изображений, учёт скидок NPC,
проверка ограничений продажи и регулярное обновление базы — отдельные задачи.

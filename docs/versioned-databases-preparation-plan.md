# Подготовка баз TBC, Classic и Forever

## Результат и границы

Подготовить три самостоятельных JSON-файла одного формата. Каждый содержит только
крафты и расходуемые реагенты своей версии игры, названия RU/EN, ссылки на иконки,
профессии и рецепты. Это план подготовки данных; загрузка в приложении, интерфейс,
store, сохранение пользовательского каталога и расчёты сайта здесь не проектируются.

Предлагаемые выходные пути:

- `public/data/classic/craftcalc-db.<build>.json`.
- `public/data/tbc/craftcalc-db.<build>.json`.
- `public/data/forever/craftcalc-db.1.60.1.70338.json` для существующего снимка.

`<build>` заменяется на выбранную полную сборку. Не создавать файл с буквальным
шаблоном в имени. Исходные CSV, кеш запросов и отчёты проверки хранить отдельно от
`public`, чтобы они не попадали на сайт. Полные сборки сохранять в именах файлов
для воспроизводимости.

## 1. Зафиксировать варианты игры и сборки

1. Classic по умолчанию трактовать как Classic Era, без сезонных рецептов SoD.
   Если нужен другой вариант, определить его до скачивания: это меняет отбор данных.
2. Для TBC зафиксировать конкретный вариант клиента и полную сборку. Не смешивать
   оригинальную 2.4.3, архивный TBC Classic и актуальную ветку только потому, что
   они относятся к одному дополнению. Брать именно вариант, для которого нужна база.
3. Для Forever исходная точка — уже подготовленный файл сборки `1.60.1.70338`.
   При обновлении выбрать новый снимок и пересобрать его отдельно.
4. Для каждого набора записать `gameVersion` (`classic`, `tbc`, `forever`),
   выбранный режим, `build`, точный продукт источника, URL источника и локали.
   Текущие названия продуктов и доступные сборки проверить при выполнении плана,
   а не угадывать по префиксу номера версии.
5. Все таблицы одной базы должны относиться к одному продукту и одной сборке.
   Не использовать условный «latest» отдельно для каждой таблицы.

Не получать Classic/TBC фильтрацией Forever по ID предмета, `ExpansionID`, уровню
предмета или отсутствию новых названий. Старый ID может иметь другой состав,
характеристики, цену или доступность в другой версии. Наличие строки в клиенте
также не доказывает доступность предмета игроку в выбранном режиме.

## 2. Подготовить исходные выгрузки

Для каждого варианта скачать с Wago таблицы выбранной сборки:

- `Item` — свойства категории предмета и исходные сведения об иконке.
- `ItemSparse` в `ruRU` и `enUS` — названия, качество, привязка, цены NPC.
- `SpellReagents` — реагенты и их количества.
- `SpellEffect` — связь заклинания с создаваемым предметом и исходные данные выхода.
- `SkillLineAbility` — связь заклинания с профессией.
- `SkillLine` — названия и связи навыков; для текущего формата достаточно `ruRU`.
- `SpellTotems` — требуемые инструменты и их категории.

Это восемь CSV на вариант, считая две локализации ItemSparse. Для Classic и TBC
нужны новые комплекты; комплект Forever уже предоставлен.

Дополнительные таблицы не являются условием первой подготовки:

- `TotemCategory` RU/EN — если нужны понятные названия категорий инструментов.
- `SpellName` RU/EN — если нужны названия рецептов, отличающиеся от названия результата.
- `SpellCooldowns` — если потребуется хранить время восстановления крафта.

Использовать явные имена вроде `ItemSparse.ruRU.<build>.csv`, а не суффиксы
`(1)`. Если выгрузки уже имеют старые имена, зафиксировать соответствие локали в
манифесте источников. Для каждого файла сохранить число строк и SHA256.

Если Wago недоступен, извлечь данные выбранного клиента через wow.tools.local.
У него задаются продукт, локаль и конфигурация сборки; официальный API Blizzard
для этой операции не требуется. Не подменять недостающую таблицу выгрузкой из
другой версии. Источник замены явно записать в метаданных.

## 3. Принять единый контракт JSON

Взять существующий `public/data/craftcalc-db.1.60.1.70338.json` за основу структуры,
но добавить явную идентичность набора: `gameVersion`, режим и продукт источника.
Три новых файла выпускать с общей новой `schemaVersion: 2`; версия `build` остаётся
отдельным параметром и не заменяет версию формата. Исходный файл пока не удалять и
не переименовывать: сначала подготовить и проверить новые выходные файлы.

У предмета сохранить согласованные семь полей:

- `itemId`.
- `names: { ru, en }`.
- `iconUrl`.
- `qualityId`.
- `bondingId`.
- `vendor` с ценами в медных монетах, размером пачки и неизвестной доступностью.
- `recipeSpellIds`.

Ключи `items` и `recipes` остаются строковыми представлениями числовых ID.
Одинаковый ID в разных базах допустим; записи принадлежат своим версиям и не
объединяются в одну общую запись.

Для рецептов сохранить существующие поля состава, профессии, выхода, инструментов
и происхождения. Альтернативные способы изготовления хранить раздельно по
`spellId`; не выбирать один рецепт на этапе подготовки данных.

Сохранить `sources`, `statistics`, `itemScope`, `iconSource`, ограничения набора
и список исключённых записей с причинами. Добавить дату подготовки снимка и
описание правил отбора. Не создавать пустые заглушки для ещё не собранных баз.

## 4. Собрать каждую базу независимо

1. Проверить заголовки CSV и уникальность ключей. У разных сборок могут отличаться
   имена и устройство столбцов: подготовить явные адаптеры источников, а не
   молчаливые подстановки нулей при отсутствующем поле.
2. Соединить локализации ItemSparse и Item по ID. Сравнить поля вне локализованного
   текста. Несовпадающие ID и отсутствующий перевод записать в отчёт, без
   сопоставления по названию или заимствования перевода другой версии.
3. Связать SpellEffect и SpellReagents по SpellID, SkillLineAbility — по Spell,
   SkillLine — по ID. Учесть дочерние навыки через ParentSkillLineID, если они есть.
4. Отбирать эффекты обычного создания предмета (`Effect = 24`) с положительным ID
   результата и связью с нужной профессией. Это сохраняет нынешнюю границу набора:
   обычные чары без создаваемого предмета и другие виды эффектов не включаются.
5. Проверять наличие результата и всех расходуемых реагентов, положительные целые
   количества, повторы реагентов и неоднозначную профессию. Повреждённый состав
   исключать целиком с причиной.
6. Не считать связь с профессией достаточным подтверждением доступности рецепта.
   Для Classic Era отдельно проверить сезонные и скрытые записи. При необходимости
   подготовить список включений/исключений с источником для каждой правки.
   Непроверенный набор явно обозначать как кандидаты из таблиц клиента.
7. Сформировать `items` строго как объединение результатов включённых рецептов
   и их непосредственных расходуемых реагентов. Другие предметы не добавлять.
8. Требования инструментов сохранить в рецептах отдельно от состава. Предмет,
   используемый только как инструмент, не расширяет каталог; его ID может быть
   внешней ссылкой. Отсутствующую категорию не превращать в ID реагента.
9. Построить `recipeSpellIds` из итоговых рецептов. Все ссылки должны быть
   согласованы в обе стороны. Статистику вычислять после всех исключений.

Для Forever сначала воспроизвести существующие результаты: 2 344 предмета и
1 984 рецепта при прежних правилах отбора. Если новый отбор доступности меняет
состав, показать отдельный отчёт с причинами, а не сохранять прежние цифры вручную.
Для Classic/TBC заранее не обещать количество предметов или рецептов.

## 5. Сохранить корректную семантику выхода и цен

Выход не выводить по одному полю без проверки схемы конкретной сборки. Сохранить
`quantity: null` для неподтверждённых данных, исходные параметры эффекта и отдельно
`baseQuantityCandidate`, если его можно получить. Не использовать правило
«нулевой базовый выход означает 1» или универсальное прибавление единицы.

Если выход подтверждается дополнительным источником, сохранить происхождение
этого подтверждения. Переменный выход не сводить молча к фиксированному числу.
Массовое подтверждение выхода — самостоятельный этап, который можно отложить.

Цены NPC сохранить из собственной версии в `vendor`. Проверить единицы и смысл
`BuyPrice`/`VendorStackCount` для выбранной схемы; не умножать и не делить цену
пачки без подтверждения. Ноль сохранять как ноль, отсутствие данных — как `null`.
Ненулевой BuyPrice не считать доказательством продажи предмета торговцем.

Согласованное ранее назначение цен — значения по умолчанию для незаданных цен
покупки/продажи. Подготовка файлов сохраняет эти значения; применение в проекте
в текущий план не входит.

## 6. Заполнить ссылки на иконки

1. Для каждой базы использовать свой endpoint предмета:
   `https://nether.wowhead.com/{gameVersion}/tooltip/item/{itemId}`.
   Возможные значения gameVersion: `classic`, `tbc`, `forever`.
2. Сначала проверить небольшую партию: обычный реагент, старый общий предмет,
   предмет выбранного дополнения или режима. Проверить ID/ссылку предмета в ответе,
   английское название и корректное имя иконки.
3. Затем запускать скрипт с низкой параллельностью, паузами, таймаутами и
   ограниченными повторами. При 403/429 остановиться или соблюдать Retry-After.
   Полные tooltip не выводить в чат.
4. Кешировать результаты по паре `(gameVersion, itemId)`. Совпадающий ID в другой
   версии не является достаточным основанием для повторного использования ответа.
5. Для Forever можно использовать уже полученные ссылки из существующей базы,
   если версия и ID совпадают и предмет остался в итоговом наборе.
6. Несовпадение названия, 404 или некорректный ответ записывать в отчёт; `iconUrl`
   оставлять пустым до разбора. Не обращаться автоматически к другой версии.
7. Из корректного имени иконки сформировать существующий URL CDN Wowhead. Сами
   изображения не скачивать. Проверить несколько конечных картинок по статусу
   HTTP и Content-Type; наличие строки URL не доказывает доступность всех картинок.

Endpoint tooltip недокументирован: его работоспособность нужно проверять во время
подготовки. Для Forever он уже проверен на всей существующей базе; это не является
проверкой Classic/TBC.

## 7. Проверить и выпустить файлы

- Разобрать каждый сохранённый JSON общей схемой и проверить метаданные версии.
- Проверить все ссылки, обратные списки рецептов и положительные количества.
- Убедиться, что набор предметов в точности равен результатам и реагентам рецептов.
- Проверить локали, варианты рецептов, инструменты и неизвестный выход.
- Проверить, что цены, состав и перевод каждого набора получены из его источников.
- Выполнить сравнение наборов: пересечение ID допустимо, но отличия в значениях
  не должны пропасть после объединения кешей или повторного использования данных.
- Проверить несколько известных рецептов каждой версии по дополнительному
  источнику той же версии; особенно новые рецепты TBC/Forever и сезонные исключения.
- Не отклонять полный справочник только из-за циклов между альтернативными
  рецептами. Это набор способов получения, а не один выбранный граф крафта.
- Сформировать отчёт по каждой версии: источники, сборка, количества, распределение
  по профессиям, исключения, пропуски переводов и иконок, неизвестный выход.
- Сортировать ключи стабильно, форматировать только созданные файлы, проверить
  JSON и `git diff --check`. Записать SHA256 итоговых файлов в отчёт.
- Повторная сборка из тех же CSV и кеша должна давать те же данные. Дату генерации
  проверять отдельно от содержимого, либо фиксировать её как дату снимка.
- Публиковать окончательные имена только после проверок; не заменять готовую базу
  незавершённой. Коммит и push выполнять только по прямой просьбе.

## Очерёдность выполнения

Сначала выбрать сборки Classic и TBC и собрать их CSV. Затем подготовить единый
воспроизводимый конвертер и проверить его на имеющемся Forever. После этого
независимо собрать Classic и TBC, заполнить иконки, выполнить проверки и выпустить
три файла вместе с отчётами. До этого шага текущий JSON Forever сохраняется.

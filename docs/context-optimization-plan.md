# План уменьшения контекста при работе с CraftCalc

Статус: реализовано 17.10.2026. Ниже сохранён исходный план и добавлен отчёт.

Цель — позволить читать код и инструкции по отдельному сценарию, сохранив
поведение приложения, проверки данных и статическую архитектуру. Количество
файлов и размер отдельного файла сами по себе не являются критериями успеха.

## Порядок работы

Этапы выполнять последовательно, небольшими изменениями. После каждого изменения
показывать файлы, цель и фактические результаты проверок. Коммит и push — только
по прямой просьбе пользователя. Не совмещать перенос с исправлением поведения.

Перед каждым этапом повторно проверять `git status`, затрагиваемый код, места
использования и ближайшие тесты: состояние проекта могло измениться после аудита.
Названия новых файлов ниже — предлагаемые; перед созданием проверить, нет ли
подходящей реализации в проекте.

## 1. Зафиксировать сравнимую исходную точку

Без изменения исходников составить для трёх задач минимальные наборы чтения:

- изменение сопоставления импортируемого предмета;
- изменение предпросмотра импорта из базы;
- изменение массового редактирования цен.

Для каждого набора записать пути, число символов и основание для включения:
обязательная инструкция, реализация, вызывающий код или ближайший тест.
Отдельно учитывать обязательные инструкции и код. Использовать одинаковые
границы чтения до и после: если достаточно части файла, учитывать именно её.

Проверка: наборы покрывают путь данных соответствующего сценария; исходные
показатели и методика записаны в этот документ перед началом переноса.
Экономию токенов без отдельного измерения токенизатором не заявлять.

## 2. Уменьшить обязательный объём инструкций UI

Затрагиваемые файлы:

- `AGENTS.md`;
- `.cursor/rules/ui-and-features.mdc`;
- `docs/development.md`;
- новые `docs/ui-components.md` и `docs/ui-features.md`.

Шаги:

1. Разделить содержимое существующего правила на общие требования, краткую карту
   компонентов и подробные описания отдельных сценариев.
2. Сохранить обязательные требования в корневом `AGENTS.md` и краткую карту
   с ссылками в `docs/ui-components.md`. Детали страниц, редакторов, планировщика
   и анимаций конкретных компонентов перенести в `docs/ui-features.md`.
3. Указать в корневых инструкциях: перед правкой UI читать краткую карту,
   затем только относящиеся к задаче разделы подробного описания и код.
   Не превращать подробную документацию в обязательное чтение целиком.
4. Проверить все ссылки на старое правило. После переноса всех требований
   и обновления ссылок удалить заменённый файл, не создавая новых `.mdc`
   или настроек Cursor. Остальные тематические правила в этом этапе не менять.

Сохранить требования доступности, переиспользования, десктопного интерфейса,
`prefers-reduced-motion` и корректного завершения удаления строк.

Проверка: сопоставить исходные требования с новыми местами, проверить локальные
ссылки, Prettier изменённых Markdown-файлов и `git diff --check`.
Готовность: обычная правка UI больше не требует чтения всех подробных описаний.

## 3. Выделить контракты и сопоставление импорта из store

Основные файлы:

- `src/store/useCraftStore.ts`;
- новые `src/domain/recipe-import.types.ts` и `src/domain/imported-item-matching.ts`;
- `src/domain/reference-database-import.ts`;
- потребители типов и сопоставления в редакторах и формах импорта;
- `docs/development.md` и соответствующие тематические правила.

Сначала через поиск собрать все импорты типов, `findImportedItem`, тесты,
экспорты и обращения. Переносить двумя отдельными изменениями:

1. Перенести предметные типы импорта в domain и обновить всех потребителей.
   Контракты действий store, `WorkspaceRequest` и статус persistence оставить
   в слое store. Не создавать общий файл для всех типов проекта.
2. Перенести чистое сопоставление предметов и связанные проверки неоднозначности.
   Сохранить приоритет ID источника, совместимость версий, поиск по RU/EN
   и исключение заданных ID. Проверку внешних данных и атомарную запись
   сохранить в действиях store.

Не вводить систему slices, фабрики действий или промежуточные реэкспорты
ради совместимости внутренних импортов. Выделение самих больших действий
рассматривать отдельно, только если после этих шагов оно всё ещё необходимо.

Проверки: ближайшие тесты сопоставления и импорта, затем `npm run check`
и `npm run build` после каждого изменения кода. При необходимости перенести
существующие точечные тесты сопоставления рядом с новым модулем, сохранив
интеграционные проверки атомарности, цен, рецептов и изоляции workspace.
Готовность: domain не импортирует контракт импорта из Zustand-модуля;
сопоставление можно изучать без чтения действий сохранения и планировщика.

Проверки: сравнить перечень и число тестов до и после; запустить затронутые
файлы отдельно и вместе, затем `npm run check` и `npm run build`.
Готовность: не потеряны проверки и их изоляция; тест нужного сценария находится
по имени файла. Ускорение запуска без измерения не заявлять.

## 5. Разнести компоненты формы базы по файлам

Основной файл — `src/features/reference-database/ReferenceDatabaseForm.tsx`.
В той же feature создать `ReferenceReview.tsx` и `ReferenceBrowser.tsx`.

1. Сначала перенести уже существующий `ReferenceReview`, затем отдельным
   изменением — `ReferenceBrowser`.
2. В исходном файле оставить загрузку базы, повтор после ошибки и оболочку
   со сбросом состояния по версии игры.
3. Общие props вынести в локальный файл типов только при необходимости
   для нескольких компонентов; избежать циклических импортов.
4. Сохранить существующие UI-компоненты и CSS, ключи компонентов, начальные
   значения состояния, эффекты, защиту черновиков и обработку ошибок.
   Не объединять этот перенос с формой Wowhead.

Проверки: `ReferenceDatabaseForm.test.tsx`, тесты загрузчика и импорта в store,
затем `npm run check` и `npm run build`. На десктопе проверить поиск,
пагинацию, выбор альтернативного рецепта, предпросмотр и подтверждение.
Обновить карту компонентов и рабочую памятку.
Готовность: изменение предпросмотра локализовано в отдельном компоненте;
публичный API формы и поведение загрузки сохранены.

## 6. Выделить управление черновиками массовых цен

Основной файл — `src/pages/ItemsPage.tsx`.
Предлагаемый новый файл — `src/features/item-editor/useBulkPriceDraft.ts`.

Перенести состояние черновиков, начало редактирования, изменение значения,
отмену, сохранение и вычисление наличия несохранённых изменений.
Передавать данные и действие сохранения через аргументы хука; запись каталога
по-прежнему выполняет `setItemPrices`. Регистрацию в draft guard оставить
у страницы либо перенести вместе с состоянием без двойной регистрации.

Сохранить различие `null` и нуля, отсутствие записи для неизменённых цен,
сохранение источников TSM, работу поиска и защиту при смене версии.
Удержание удаляемых строк, дерево, drag-and-drop и диалоги этим этапом не менять.

Проверки: профильные тесты цен и переключения версии, затем `npm run check`
и `npm run build`. На десктопе проверить сохранение, отмену и предупреждение
о несохранённых изменениях. Обновить карту и описание ответственности хука.
Готовность: сценарий массовых цен читается отдельно от разметки дерева.

### Вывод по замерам

Основной измеренный выигрыш даёт чтение инструкций UI по сценарию. Выделение
модулей улучшает поиск и позволяет не читать соседние обязанности, но само по
себе не гарантирует уменьшения минимального объёма кода: импорты, сигнатуры
и общие типы тоже занимают место. Часть общих требований перенесена в корневой
`AGENTS.md`, поэтому набор без UI стал больше; это явно учтено выше.

Новые переходы: контракт и сопоставление импорта — два соседних модуля domain;
предпросмотр — отдельный компонент и файл props; массовые цены — отдельный хук
и общая тестовая фикстура. Реализации находятся по карте и рабочей памятке.
Экономия токенов и ускорение тестов не измерялись и не заявляются.

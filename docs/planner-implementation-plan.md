## 1. Задача и утверждённые требования

Пользователь выбрал сочетание отдельного планировщика и общей панели покупок:

1. Добавить самостоятельный раздел приложения с названием «Планировщик».
2. На остальных страницах показывать справа боковую панель «Список покупок».
3. В родительских строках каталога добавить кнопку с иконкой продуктовой тележки.
4. По нажатию этой кнопки показывать числовое поле количества.
5. Если рецепт создаёт несколько предметов, шаг поля должен равняться
   `recipe.outputQuantity`. Для выхода 3 увеличение/уменьшение происходит на 3.
6. Планировать изготовление заданного количества предметов, объединять общие
   реагенты, учитывать промежуточный крафт и целые партии.

Под «родительскими строками» в этом документе понимаются корневые строки
`RootItemRow` разделов «Крафты», «Реагенты» и «Избранное». Вложенным строкам
`ReagentItemRow` кнопку тележки в первой реализации не добавлять.

Предыдущий переключаемый макет служит визуальным ориентиром. Его демонстрационные
рецепты, цены и JavaScript не переносить в расчёты приложения. Реализация должна
использовать текущий каталог, пользовательские способы получения и реальные
используемые цены приложения.

## 2. Предложенные решения для деталей, не заданных пользователем

Следующие пункты — рекомендуемые значения по умолчанию для реализации,
а не дополнительные уже утверждённые пользователем требования. Если в новом чате
появится другое указание пользователя, оно имеет приоритет.

### 2.1. Количество и кнопка тележки

- Количество означает число готовых предметов, а не число нажатий «создать».
- Первый клик добавляет цель в план: для предмета с рецептом количество равно
  `outputQuantity`, для предмета без рецепта — 1. Поле появляется и получает фокус.
- Тележка выбранного предмета имеет заметное активное состояние и `aria-pressed`.
- Повторный клик удаляет цель из плана и скрывает поле. Это не удаляет предмет
  из каталога и не меняет рецепты.
- Значение общее для всех разделов. Изменение количества одного предмета
  в «Избранном» обновляет его количество в «Крафтах» и «Планировщике».
- Поле имеет `min={1}` и `step={item.recipe?.outputQuantity ?? 1}`.
- В store попадает только положительное безопасное целое число. Ноль, дробь,
  `NaN`, бесконечность и переполнение не становятся сохранённой целью.
- Удаление выполняется повторным нажатием тележки или отдельной кнопкой удаления
  в планировщике; не привязывать удаление к промежуточному пустому вводу.
- Шаг не означает запрет ручного ввода некратного положительного количества.
  Например, при выходе 3 можно запросить 4 предмета: план рассчитает 2 крафта,
  получение 6 предметов и остаток 2. Сам запрос остаётся равным 4.
- Если `outputQuantity` изменился, сохранить запрошенное количество предметов,
  обновить шаг поля и пересчитать партии и остатки. Не умножать прежнее количество
  на новый выход и не округлять сохранённый запрос молча.

### 2.2. Какие предметы можно добавить

- Предмет с рецептом становится целью изготовления. Корневая цель явно означает
  желание изготовить предмет; автоматический выбор покупки/крафта применяется
  к её реагентам, а не заменяет эту цель покупкой готового изделия.
- Предмет без рецепта становится дополнительной прямой покупкой. Так тележка
  остаётся полезной и в разделе «Реагенты».
- На странице планировщика различать «К изготовлению» и «Дополнительные покупки».
- Отсутствие профессии не запрещает явно запланированный корневой крафт,
  как и существующий ручной выбор `craft`. Отобразить предупреждение о профессии;
  правила `auto` для вложенных реагентов сохраняются.
- Если у выбранного предмета удалили рецепт, сохранить количество и перевести
  цель в дополнительные покупки. Отобразить, что у цели больше нет рецепта.
- Если удалили сам предмет, атомарно удалить его цель из плана.

### 2.3. Общая панель и сохранение

- Один план на каждую версию игры; несколько именованных планов пока не нужны.
- План сохраняется в браузере и входит в общую резервную копию JSON.
- Переход между разделами не очищает план. Смена версии показывает план этой
  версии; возврат восстанавливает предыдущий.
- Справа на всех разделах, кроме «Планировщика», находится одна общая панель.
  Это включает существующую заглушку «Выгодные», но не требует её реализации.
- На странице «Планировщик» внешняя панель скрыта: полный список покупок
  показывается внутри страницы тем же компонентом.
- При пустом плане панель остаётся с короткой подсказкой, откуда добавлять цели.
- Отметки «Куплено», складские остатки и учёт частичных покупок не обязательны
  для первой реализации. Их отсутствие не должно задерживать основной сценарий.

## 4. Структура данных и хранение

Рекомендуемая исходная структура:

```ts
interface PlannerTarget {
  itemId: ItemId
  quantity: number
}

interface CraftPlan {
  targets: PlannerTarget[]
}

// В существующем VersionWorkspace:
planner?: CraftPlan | undefined
```

Типы плана разместить в `src/domain/planner.types.ts`, в `item.types.ts` добавить
ссылку на новый тип. Массив сохраняет порядок добавления; один `itemId` допускается
только один раз. Отдельный массив порядка в первой реализации не нужен.

Не сохранять вычисляемые цены, итоговые списки реагентов, профессии, наименования,
иконки, партии, остатки и снимки TSM внутри `planner`.

Рекомендуемые действия `useCraftStore`:

- `setPlannerQuantity(itemId, quantity)` — добавить или изменить количество;
  неизвестный ID и некорректное количество отклонить без частичного обновления.
- `removePlannerTarget(itemId)` — убрать только цель.
- `clearPlanner()` — очистить только план активной версии.

Повторная установка того же значения не должна создавать лишнюю запись.
Не переключать выбранную цель между покупкой/крафтом отдельным сохраняемым полем:
для первой версии это определяется текущим наличием рецепта.

Селекторы: активный план, список целей с актуальными предметами, количество цели
по `itemId`. Не создавать второй store с копией корзины.

Для добавочного необязательного поля можно сохранить существующие
`STORAGE_VERSION = 1` и `EXPORT_VERSION = 1`: текущая запись или резервная копия v1
без `planner` означает пустой план. Это не поддержка прежнего формата
`craft-calc-data` и не повод добавлять запрещённые адаптеры старого каталога.

Валидация persistence и импорта:

- `planner` отсутствует — допустимо; пустой план — допустимо.
- Количество — положительное безопасное целое; ID — непустая строка.
- Цели уникальны и ссылаются на предметы своего workspace.
- Некорректный явно переданный план отклоняет весь импорт до замены данных.
- Экспорт/импорт сохраняет планы всех трёх версий.
- Сброс создаёт пустые планы; ошибка записи обрабатывается существующей защитой.
- Удаление предмета очищает соответствующую цель в том же обновлении store.
  Не менять попутно существующее удаление этого предмета из чужих рецептов.
- Редактирование, повторный импорт рецепта, смена цен, профессий и источников
  сохраняют цели и пересчитывают их производное представление.

## 5. Расчёт плана

Добавить чистую функцию в `src/domain/planner.ts`, например
`calculateCraftPlan(catalog, targets, ownedProfessions, prices)`.
В `domain` не должно быть React, Zustand, DOM, сетевых запросов и localStorage.

### 5.1. Отдельный расчёт партий

Нельзя получать закупку умножением существующей стоимости единицы на количество:
она допускает дробную долю промежуточного крафта, а план требует целые партии.
Существующие формулы каталога при этом менять не нужно.

Алгоритм должен работать с общей потребностью всех целей:

1. Проверить входные цели и доступную часть графа. Обнаруженные отсутствующие
   предметы, циклы, пустые/некорректные рецепты и переполнение вернуть понятными
   диагностическими результатами; не уходить в бесконечный обход.
2. Для используемых строк рецептов определить способ получения. Ручные `buy`
   и `craft` сохранить. Для `auto` переиспользовать существующую семантику
   из `calculations.ts` и текущий `PriceContext`.
3. Не вводить отдельный оптимизатор `auto` по цене полной партии: это изменило бы
   поведение по сравнению с каталогом. Выбор метода прежний, количество закупки
   и стоимость плана учитывают целые партии.
4. Построить зависимости и порядок обработки от потребляющих предметов
   к их реагентам. Принадлежность к разделу каталога не ограничивает обход.
5. Сначала собрать все запросы на изготовление одного предмета от всех родителей
   и его собственной цели. Только затем вычислить
   `craftCount = Math.ceil(requiredCraftQuantity / outputQuantity)`.
6. `producedQuantity = craftCount * outputQuantity`,
   `surplusQuantity = producedQuantity - requiredCraftQuantity`.
7. В реагенты этого предмета передать `craftCount * recipeLine.quantity`.
8. Потребность купить предмет суммировать отдельно. Предмет с выбранным `buy`
   не раскрывать в его реагенты.
9. Объединить конечные покупки по локальному `itemId`. Одно имя или Wowhead ID
   не заменяет локальную идентичность и не объединяет разные версии.
10. Для отображения этапов обратить зависимости: сначала получить промежуточные
    изделия, затем изготовить использующие их предметы.

Обход, который независимо рассчитывает каждую корневую цель, округляет каждую
ветку и только потом складывает покупки, для этой задачи неверен.

### 5.2. Общие реагенты и разные способы получения

- Вести отдельные количества `buy` и `craft` для одного предмета.
- Если один родитель явно требует покупку, а другой — крафт, сохранить оба
  решения. Нельзя заменить явную покупку остатком крафта другого родителя.
- Объединять запросы на крафт одного предмета между родителями и отдельной
  производственной целью; округление партии выполнять один раз на их сумму.
- Конечная цель промежуточного предмета означает дополнительное количество
  к потреблению в рецептах, а не доступный запас для других целей.
- Не учитывать существующий запас, «уже куплено» и остатки прошлых запусков.
  Здесь остаток — только дополнительный выход текущего рассчитанного плана.
- Для объяснения сохранять в производном результате связи «нужен для»:
  из каких целей/рецептов пришла потребность.

### 5.3. Цены и финансовые итоги

- Покупка и продажа берут используемые цены через `resolveItemPrice`, включая
  TBC `individual`/`tsm`. Источник и недоступность цены сохраняют текущий смысл.
- Стоимость строки покупки: количество × используемая цена покупки.
- Неизвестная цена не равна нулю. Строка с известным количеством остаётся
  в списке даже при отсутствии цены.
- Если не все цены известны, полный итог равен `null`; отдельно можно показать
  «Известная часть: …» и число строк без цены, не выдавая эту сумму за полную.
- Для цели крафта продажа относится только к запрошенному конечному количеству.
  Промежуточные изделия, которые расходуются в рецептах, и излишки партии
  не создают повторную выручку.
- Стоимость производства включает все партии, необходимые для целей.
  Не вычитать условную продажную стоимость остатков из затрат.
- Дополнительные прямые покупки показывать отдельным подытогом бюджета.
  Они не являются продажей и не уменьшают прибыль производственной части.
  При совпадении материала объединять строку закупки, сохраняя разделение
  производственного количества и дополнительной прямой покупки.
- Общий бюджет = производственные покупки + дополнительные прямые покупки.
- Выручка = сумма `target.quantity * salePrice` только целей изготовления.
  Прибыль = эта выручка − производственные покупки.
- При неизвестной цене продажи или производственных затрат соответствующая
  выручка/прибыль равна `null`. Не подменять её частичным известным результатом.
- При отсутствии целей изготовления показывать бюджет покупок, а не искусственную
  «прибыль 0». Комиссии аукциона в этой задаче не добавлять.

### 5.4. Состав производного результата

Уточнить типы при реализации, сохранив следующие данные:

- Цели: запрос, способ получения, количество крафтов, выход и избыток.
- Покупки: `itemId`, общее количество, количество для производства/прямой покупки,
  цена единицы, источник цены, сумма или `null`, зависимости «нужен для».
- Производственные шаги: предмет, число крафтов, общий выход, потребление и остаток.
- Итоги: общий бюджет, производственный бюджет, дополнительные покупки,
  выручка, прибыль, известная часть и недостающие цены.
- Диагностика ошибок и предупреждений, включая недоступную профессию.

Названия, переводы и форматирование денег остаются в UI. Пустой план возвращает
пустые списки без ошибок. Расчёт не изменяет каталог и входные массивы.

## 6. Интерфейс и переиспользование

### 6.1. Общий контрол цели

Добавить `src/features/planner/PlanQuantityControl.tsx` и локальные стили.
Это композиция `IconButton` с тележкой и существующего `NumberInput`, а не
параллельная реализация числового поля.

Props должны описывать предмет/название, выбранное количество, шаг и обработчики.
Сам контрол не читает store и не меняет каталог. Он используется в `RootItemRow`

## 9. Контрольные сценарии расчёта

Все числа ниже — синтетические тестовые данные, а не игровые рецепты.

1. Один рецепт: 2 реагента по 10 меди, выход 1; запрос 5 — купить 10 реагентов,
   затратить 100 меди, выполнить 5 крафтов.
2. Выход 3; первый клик тележки ставит 3, увеличение ставит 6.
   Ручной запрос 4 — выполнить 2 крафта, произвести 6, остаток 2.
3. Две разные цели требуют по 1 промежуточному предмету; его рецепт даёт 2
   за один крафт из 3 базовых реагентов. Итог — один промежуточный крафт
   и 3 базовых реагента, а не два крафта и 6 реагентов.
4. К предыдущему случаю добавить самостоятельную цель на 1 промежуточный предмет:
   суммарно нужно 3, изготовить 4 за 2 крафта, купить 6 базовых реагентов,
   остаток 1. Выручку считать только по конечным целям.
5. Один родитель покупает 1 промежуточный предмет, другой крафтит 1:
   в закупке есть 1 готовый промежуточный предмет и реагенты одного крафта.
   Избыток крафта не отменяет явно выбранную покупку.
6. Корневая цель без рецепта — прямая покупка, без производственных шагов
   и без искусственной выручки.
7. Прямая дополнительная покупка совпадает с производственным реагентом:
   одна строка с суммарным количеством, но отдельные подытоги бюджета.
8. Нет цены одного реагента: количество известно, полный бюджет `null`,
   известная часть подписана отдельно, план не исчезает.
9. Цена реагента равна 0: это бесплатная покупка с известной нулевой стоимостью.
10. TBC: `individual`/`tsm`, смена рынка, профессии и снимка пересчитывают план
    теми же источниками, что каталог. Недоступный TSM не подменяется ручной ценой.
11. У предмета изменили выход 3 → 5: запрос 6 сохраняется, шаг становится 5,
    нужно 2 крафта, выход 10, остаток 4.
12. Цель или общий реагент удалены через существующий store: план не содержит
    висячей цели, оставшиеся рецепты учитывают текущее поведение удаления.
13. Повреждённый граф и переполнение количества дают диагностируемую ошибку,
    не зависание, `Infinity` или правдоподобный частичный полный итог.

## 10. Критерии готовности

- Раздел «Планировщик» доступен из меню и из общей панели.
- Тележка и количество есть только в корневых строках; состояние синхронно
  в крафтах, реагентах, избранном и планировщике.
- Шаг поля соответствует выходу рецепта; партии и остатки рассчитаны корректно.
- Общий реагент округляется после объединения всех нуждающихся в нём крафтов.
- Покупка/крафт соблюдают сохранённые настройки и существующие правила `auto`.
- Справа на остальных страницах показан единый актуальный список покупок;
  на странице планировщика нет его дублирующей внешней панели.
- Смена страницы не теряет цели; версии изолированы; обновление браузера
  и JSON round-trip восстанавливают планы.
- Нет выдуманных цен, двойного учёта промежуточной выручки и подмены `null` нулём.
- Корзина не ломает раскрытие, drag-and-drop, избранное, модальные редакторы
  и массовый ввод цен.
- Проверены длинные названия и текущая десктопная раскладка; адаптивные стили
  и проверки на других размерах экрана не добавлены.
- Пройдены профильные тесты, `npm run check`, `npm run build`; если проверка
  не запустилась или нашла исходную проблему, это отражено в отчёте.
- README и тематические правила описывают фактически реализованное состояние.
- Коммит и push не выполнялись без отдельной просьбы пользователя.

# План разделения CraftCalc по версиям игры

План составлен 12.10.2026 по текущему коду и подготовленным локальным JSON.
Реализация приложения в рамках этого плана не выполняется.

## Согласованные требования

- Версии: Forever, TBC и Classic.
- Выбор версии доступен в настройках и по клику на логотип сверху слева.
- Forever получает голубую палитру на основе текущей темы, TBC — тёмно-зелёную,
  Classic — коричневатую. Интерфейс остаётся тёмным и только десктопным.
- Каждая версия имеет независимый пользовательский каталог: набор крафтов и
  реагентов, цены, выбранные рецепты и способы получения.
- Пользователь добавляет нужные предметы через «Из базы». Весь справочник
  автоматически на страницы не переносится.
- Обратная совместимость не требуется. Старые данные и резервные копии не
  переносятся; предметы добавляются заново из новых баз.
- Сохраняются статическая архитектура GitHub Pages и строгие настройки TypeScript.

## Что уже есть и что требуется подключить

Подготовлены три справочника `schemaVersion: 2`:

- Classic: `public/data/classic/craftcalc-db.1.14.4.51829.json`, режим `era`;
  1 436 предметов и 1 133 рецепта.
- TBC: `public/data/tbc/craftcalc-db.2.5.6.69795.json`, режим `anniversary`;
  2 363 предмета и 1 974 рецепта.
- Forever: `public/data/forever/craftcalc-db.1.60.1.70338.json`, режим `beta`;
  2 344 предмета и 1 984 рецепта.

Сейчас `reference-database-loader.ts` загружает прежний Forever-файл из корня
`public/data`, схема принимает только schema 1 и фиксированную сборку, а
`reference-database-import.ts` явно подставляет `forever`. Store хранит один
`items`, один список профессий и использует ключ `craft-calc-data`.

Логотип в `Sidebar.tsx` пока не является кнопкой. Цвета частично вынесены в
`global.css`, частично заданы напрямую в CSS компонентов. У приложения уже есть
выборочное добавление из базы, ручное создание и импорт Wowhead — их нужно
перевести на контекст активной версии. Импорт из версии, отличной от текущей,
запретить с предупреждением о несовпадении версий; данные при этом не добавлять.

## Предлагаемая модель

### Реестр версий

Добавить `src/domain/game-version.ts` с типом `GameVersion` и реестром трёх
версий. Для каждой записи задать ID, название, относительный путь JSON, сборку,
режим, продукт, версию Wowhead и доступные профессии. Реестр — единый источник
для переключателей, загрузчика и проверки соответствия базы выбранной версии.

ID приложения и версия Wowhead сейчас совпадают, но связь оформить явно:
логика сайта не должна зависеть от того, что внешний сервис использует те же ID.
Версия по умолчанию — Forever, как предложение для нового чистого запуска.

### Данные пользователя

Предлагаемая сохраняемая структура:

```ts
interface VersionWorkspace {
  items: ItemCatalog
  ownedProfessions: Profession[]
}

interface VersionedCraftData {
  activeVersion: GameVersion
  workspaces: Record<GameVersion, VersionWorkspace>
  currencyDisplay: CurrencyDisplayMode
  itemLanguage: ItemLanguage
}
```

Цены, рецепт, разделы и выбор получения уже находятся внутри `Item` и его рецепта,
поэтому автоматически изолируются вместе с каталогом. Профессии тоже относятся
к версии: наличие профессии в TBC не должно менять расчёт в Forever.
Язык названий и вид валют остаются общими настройками интерфейса.

Не хранить отдельную копию активного `items` рядом с `workspaces`. Добавить
селекторы активного каталога и профессий в `craft.selectors.ts`, перевести на них
потребителей. Все действия `useCraftStore` изменяют только нужный workspace.
Расчёты получают его каталог и профессии; формулы в `src/domain` сохраняются.

Одинаковый Wowhead itemId в разных версиях не означает общий пользовательский
предмет. Ручные предметы также принадлежат workspace. Ссылки рецепта проверяются
только внутри своего каталога, а удаление реагента действует только в своей версии.

### Чистый запуск и сохранение

- Использовать новый ключ, например `craft-calc-versioned-data`, и собственную
  начальную версию формата. Старый ключ не читать, а удалять при запуске, чтобы не занимал место.
- Создать три пустых workspace; цены и рецепты появятся после нового добавления.
- Последнюю выбранную версию сохранять. Переключение не очищает её каталог:
  при возвращении пользователь видит свои ранее введённые данные.
- Не писать миграции прежнего каталога и адаптеры старых экспортов.
- Проверять новый формат Zod и граф каждого workspace до применения данных.
- Сохранить обработку повреждённой записи и отказа localStorage. Ошибка не должна
  приводить к незаметной потере новой записи или ложному сообщению о сохранении.

## Подключение новых справочников

1. Перевести `reference-database.schema.ts` и типы на schema 2. Проверять
   `gameVersion`, `mode`, `product`, `build`, происхождение иконок и связи данных.
   После разбора сверять метаданные с записью реестра выбранной версии.
2. Поддержать поля `vendor.stackCount` и `vendor.availability`, неизвестный выход,
   альтернативные рецепты и внешние инструменты. Не валидировать весь справочник
   как один рабочий граф: альтернативные способы получения могут давать циклы.
3. Добавить `jewelcrafting` в модель профессий. Списки в настройках, редакторах
   и поиске ограничить профессиями выбранной версии из реестра, согласованными
   с метаданными JSON. TBC показывает ювелирное дело, Classic и Forever — нет.
4. Загрузчик получает версию, строит путь через `import.meta.env.BASE_URL` и
   загружает только запрошенный справочник. Кеш запросов и индексов разделить
   по версии и сборке; ошибки разрешают повторную загрузку своей базы.
5. В `ReferenceDatabaseForm` передавать активную версию. Поиск, выбор рецепта,
   предпросмотр, происхождение данных и добавление используют только её индекс.
6. Убрать фиксированный `forever` из адаптера импорта. Предметы, результат и
   реагенты получают правильную версию источника. Повторное добавление
   переиспользует предметы только внутри текущего workspace.

Справочники остаются неизменяемыми файлами. Пользовательские цены и правки
рецептов хранятся только в store и не изменяют JSON базы. Обновление сборки
справочника не перезаписывает уже настроенные предметы пользователя.

Все `output.quantity` в трёх базах сейчас равны `null`. При добавлении крафта
сохранить обязательное подтверждение положительного целого выхода; кандидат
из эффекта не считать подтверждённым значением и не добавлять единицу автоматически.
Пользователь выбирает один активный рецепт из альтернативных; его выбранный граф
проходит текущую проверку ссылок и циклов перед атомарной записью.

В базах находятся клиентские NPC-цены, а не актуальные рыночные цены. Показывать
их с происхождением в предпросмотре; не представлять как цену аукциона. Для нового
формата безопаснее оставить рыночные поля неизвестными до ввода или явного
принятия пользователем значения базы. Неизвестная цена и ноль различаются;
повторное добавление не заменяет заданную пользователем цену. Не вводить
неподтверждённый пересчёт цены пачки через `stackCount`.

## Переключение в интерфейсе

### Две точки выбора с одним обработчиком

- В настройках добавить группу «Версия игры» с тремя вариантами.
- Логотип сделать семантической кнопкой. По клику открывать компактный список
  Forever / TBC / Classic, отмечать текущую версию. Под логотипом постоянно
  показывать её название; режим и сборку можно показывать в настройках.
- Оба элемента вызывают общий сценарий переключения из `App`; отдельного
  локального состояния версии в настройках или Sidebar не создавать.
- Переключение в настройках применяется сразу, как существующие настройки;
  окно остаётся открытым и показывает профессии новой версии.
- Выбор уже активной версии ничего не сбрасывает.

### Порядок переключения

1. Проверить несохранённые изменения: формы предмета/рецепта, пакет цен,
   предпросмотр импорта и загруженные, но не применённые названия.
2. Если они есть, показать выбор «Отменить переключение» / «Переключить и
   отбросить изменения». Молчаливого сохранения или потери черновика не делать.
   При отсутствии черновиков переключать сразу без подтверждения.
3. Сменить активную версию, каталог и тему. Оставить текущий раздел меню.
4. Закрыть редакторы и обнулить поиск, раскрытие дерева, черновики цен,
   выбранный предмет/рецепт в добавлении и относящиеся к прошлой версии сообщения.
   В частности, ключ страницы должен учитывать и раздел, и версию.
5. При следующем открытии «Из базы» загрузить либо взять из кеша новую базу.
   Ошибка её загрузки показывает сообщение и повтор; пользовательский каталог
   остаётся доступным, включая ручное добавление.

При реализации нужны доступные имена кнопок, обозначение текущего выбора,
управление с клавиатуры, закрытие Escape и возврат фокуса. Предупреждение
о черновиках согласовать с фокусом уже открытых диалогов.

## Изоляция импорта и асинхронных операций

- При запуске загрузки сохранить версию и идентификатор актуального запроса.
  Поздний ответ после переключения не должен менять новый UI или каталог,
  даже если пользователь успел переключиться обратно.
- Перед применением результата store проверяет ожидаемую версию. Для фоновой
  загрузки названий проверять также актуальность предмета и его источника.
- Импорт Wowhead разрешать только из версии, соответствующей активному workspace.
  Несовпадение объяснять до добавления; автоматически переключать сайт по ссылке
  или импортировать в другую версию не нужно.
- Для предметов без указанной версии при загрузке названий использовать контекст
  workspace. Перебор других версий Wowhead исключить.
- Адаптер базы и store проверяют происхождение результата и всех реагентов,
  предотвращая смешанный импорт независимо от защиты в форме.

## Цветовые темы

Устанавливать `data-game-version` на `document.documentElement`. Тогда тема
распространяется на фон документа, sidebar, диалоги и выпадающие списки в порталах.
Выбор палитры вычисляется из версии и отдельно не сохраняется.

- **Forever:** сохранить характер текущего тёмного интерфейса; усилить голубые
  поверхности и заменить основные золотые акценты голубыми.
- **TBC:** сохранить характер текущего тёмного интерфейса; использовать тёмные
  зелёные фоны и панели, зелёные акценты, светлый читаемый текст.
- **Classic:** сохранить характер текущего тёмного интерфейса; использовать тёмные
  коричневые фоны, тёплые поверхности, медные/янтарные акценты.


В `global.css` задать три набора общих токенов: фон, панели, поля, границы,
текст, акцент, hover, выбранное состояние и фокус. При необходимости добавить
токены для полупрозрачных поверхностей, фонового свечения и логотипа.

Заменить фиксированные цвета интерфейса в `Sidebar.css`, `App.css`, кнопках,
полях, редакторах, дереве и общих контролах на эти токены. Это необходимая часть
тем, иначе некоторые элементы останутся в старой палитре. Цвета золота/серебра/
меди и семантику успеха/ошибки сохранить. Проверить различимость состояний
и контраст текста во всех трёх темах на одной десктопной раскладке.

## Резервные копии нового формата

- Полный экспорт содержит три workspace, активную версию и общие настройки.
  Справочники в резервную копию не включаются: они поставляются с приложением.
- Задать новое явное имя формата и начальную версию экспорта. Версия экспорта,
  версия persistence и schema 2 справочников независимы.
- Полный импорт проверяет все каталоги, их графы и соответствие источников
  версиям, затем атомарно заменяет весь набор данных после предупреждения.
- Старые экспорты отклоняются понятным сообщением о неподдерживаемом формате.
- При ошибке файла или записи localStorage текущие данные остаются целыми.
  Сброс для восстановления явно сообщает, что очищает все три workspace.
- Экспорт/импорт одной версии и перенос предметов между версиями в первый этап
  не входят.

## Этапы реализации и проверки

### 1. Реестр версий и контракт новых баз

Файлы: новый `src/domain/game-version.ts`, `professions.ts`,
`reference-database.schema.ts`, связанные типы, фикстуры и тесты.

Проверка: все три реальные JSON принимаются; несоответствие версии/сборки,
повреждённые ссылки и неизвестная профессия отклоняются. TBC поддерживает
ювелирное дело; неизвестный выход сохраняется неизвестным.

### 2. Независимые workspace и новое сохранение

Файлы: `item.types.ts`, `item.schema.ts`, `src/store/useCraftStore.ts`,
`craft.selectors.ts`, `persistence.ts`, потребители store и ближайшие тесты.

Проверка: одинаковый предмет имеет независимые цены/рецепты; изменение, удаление
и профессии одной версии не меняют остальные. Чистый запуск не читает старую
запись. Перезагрузка восстанавливает все workspace и активную версию; повреждение
нового формата и ошибка записи не теряют данные. Расчёты используют только
выбранный каталог.

### 3. Загрузка и добавление по версии

Файлы: `reference-database-loader.ts`, `ReferenceDatabaseForm.tsx`,
`reference-database-import.ts`, `ItemAddModal.tsx`, Wowhead-импорт,
`item-names-loader.ts`, store и соответствующие тесты.

Проверка: каждый путь работает с базовым URL подпапки GitHub Pages; кеши
разделены; неверная база отклоняется; ошибка допускает повтор. Варианты рецепта
берутся из своей базы, повторное добавление сохраняет пользовательские цены,
цикл отклоняется атомарно. Поздние ответы не применяются после переключения.

### 4. Переключатели и жизненный цикл UI

Файлы: `App.tsx`, `Sidebar.tsx`, `UserSettingsModal.tsx`, `ItemsPage.tsx`,
общий компонент выбора версии и тесты пользовательских сценариев.

Проверка: настройки и логотип синхронизированы, активная версия видна, текущий
раздел сохраняется. Возврат восстанавливает свой каталог. Черновики защищены,
отмена оставляет форму и данные, подтверждение корректно очищает временный UI.
Клавиатура, Escape и возврат фокуса работают.

### 5. Три цветовые схемы

Файлы: `global.css` и CSS перечисленных компонентов с фиксированными цветами.

Проверка: просмотр всех тем на одном десктопном размере, включая настройки,
добавление, длинные названия, диалоги, портальные списки и состояния фокуса.
Адаптивные стили и проверки разных размеров экрана не добавлять.

### 6. Резервные копии и итоговый проход

Файлы: `persistence.ts`, `DataTransferControls.tsx`, `App.tsx`, их тесты;
при реализации обновить README и тематические инструкции о формате хранения.

Проверка: полный экспорт/импорт восстанавливает три независимых каталога и
настройки; старый формат отклоняется; повреждение одного workspace не вызывает
частичную замену. Итоговый сценарий: добавить одинаковый предмет в три версии,
указать разные цены и рецепты, переключиться, перезагрузить, восстановить копию.
После профильных тестов выполнить `npm run check` и `npm run build`.

Каждый этап выполнять небольшими изменениями с отчётом о файлах, цели и реально
выполненных проверках. Коммит и push — только по отдельной просьбе пользователя.

## Критерий готовности

Пользователь выбирает версию любым из двух способов, сразу видит её палитру и
свой набор предметов. Добавление предлагает только её базу. Предмет с одинаковым
ID можно независимо настроить в Forever, TBC и Classic; цены и рецепты не
переносятся между ними. Переключение, перезагрузка и новая резервная копия
сохраняют это разделение. Старые данные не требуются ни для одного сценария.

## Ограничения исходных данных

Новые файлы являются наборами кандидатов из таблиц клиента, а не доказанным
списком всех доступных игроку рецептов. Classic использует исторический снимок
Era, TBC — Anniversary, Forever — beta. План подключает именно эти наборы;
подготовка других режимов, проверка доступности каждого рецепта, подтверждение
NPC-продажи и автоматическая загрузка рыночных цен остаются отдельными задачами.

Основание: [описание подготовленных баз](versioned-databases.md), проверенные
JSON в `public/data/<version>` и текущие точки интеграции в `src`.
